## Design

- Strips are independent by the chain's tiling model: each strip reads
  shared read-only inputs and writes disjoint output rows, with fixed
  tap windows and summation order — that is exactly why the §L gate
  (tiled ≡ monolithic for ANY `strip_h`, including 1) holds. A chunk
  is just a strip of its own height, so a chunk-per-thread partition
  inherits the same byte-exactness for any worker count.
- `render_threaded(img, params, workers)`:
  - `workers: 0` → `available_parallelism()`; clamped so every worker
    gets ≥ 1 row, and by `worker_cap(h, m_total)` so total scratch
    plane rows `h + n·2·m_total` stay ≤ 2× the monolithic footprint
    `h + 2·m_total` (each chunk carries its own margin set — that is
    also the only extra CPU work: `(n−1)·2·m_total` recompute rows).
  - Output split via `data_mut().split_at_mut` into disjoint
    interleaved-RGB row slices — safe `&mut` per thread, no unsafe.
  - `std::thread::scope` — no 'static bounds, no Arc/Mutex, no new
    dependencies; a panicking worker `resume_unwind`s its payload in
    the caller (same failure mode as a sequential render).
- The strip body was extracted UNCHANGED into `render_strip(img, st,
  planes, strip_y, strip_y1, out, out_origin)` — the single code path
  behind `render` (monolithic), `render_tiled` (sequential strips) and
  `render_threaded` (chunks). Stage resolution moved unchanged into
  `ChainStages::resolve` (all plain data → `Sync` by construction).
- Preview leg (`render_pipeline` in the app) switches to
  `render_threaded(&img, &f.params, 0)`; **export keeps the sequential
  CLI path** (`cmd_film_apply` → `render_tiled`) so the memory-budget
  suites and R-REN-2 export behavior are untouched by this PR.

## Regression gates (new tests in chain.rs)

1. `threaded_equals_monolithic_bytes` — 96×512 image (real 128-row
   chunks at workers=4), workers ∈ {2,3,4,8,16} + auto (0): byte
   equality with the monolithic render. The multi-thread path executes
   regardless of the runner's core count because the worker count is
   explicit.
2. `threaded_tiny_image_clamps_workers` — 24×16 image, workers ∈
   {2,8,64}: the ≥1-row-per-worker clamp holds, bytes match.
3. `threaded_margin_heavy_matches` — veiling on with σ = 40 mm
   (hundreds of margin rows at test scale) so `worker_cap` genuinely
   engages; bytes match the monolithic reference.
4. `worker_cap_bounds_total_scratch` — the memory invariant
   `h + n·2·m ≤ 2(h + 2·m)` over a grid of (h, m, requested).
5. Existing `tiled_equals_monolithic_bytes` (strip 1/3/7/16/64) passes
   UNCHANGED — the refactor is behavior-preserving by construction.

## Notes for review

- Byte-exactness argument: chunks are strips (§L covers any partition);
  the strip body is the same function the sequential executors run;
  per-chunk scratch is sized exactly as `render_tiled` sizes a strip of
  that height; output writes are the same values to the same positions
  as `pixel_mut` wrote (interleaved row-major).
- Known trade-off: margin recompute grows with worker count
  ((n−1)·2·m_total rows); the cap keeps scratch bounded, and preview
  margins are small (mm_per_pixel is large at preview scale).
- The `render()` API and the CLI are untouched — golden/parity/hash
  tests across the repo see identical bytes.
