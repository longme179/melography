# Secure Release & Update

## Prerequisites
- Read ADR-0005 + `docs/RELEASING.md` fully. Confirm the action is owner-authorized (AGENTS §10) before starting.

## Workflow
1. Classify the change: build-only (CI artifacts) vs publish-capable (release workflow, manifest promotion, signing env). Publish-capable changes need owner pre-approval referenced in the PR.
2. **Keys:** production private keys are generated BY THE OWNER and stored only in GitHub Secrets / their signing environment. If asked to "generate the release key", stop and prepare instructions for the owner instead — the agent may generate *throwaway test keys* for S4-style dry-runs only, clearly labeled.
3. Release workflow structure: tag-triggered → builds matrix → runs tests on artifacts → attaches to a **draft** release → stops. Publishing, `latest.json` promotion, and stable-manifest changes happen only inside the `release` protected Environment requiring owner approval.
4. Manifest discipline: generated by the tooling, schema-validated, channel ID must match build channel; never hand-edited.
5. Verify invariants in CI: signature files exist for every updater-eligible artifact; updater dry-run (test channel, throwaway key) validates install + rollback-to-supersede path.
6. Recovery runbook check: for any release-affecting change, confirm RELEASING §5 (supersede-rollback, key rotation, interrupted-update) still matches reality; update it in the same PR.
7. Document precisely what was NOT run (e.g., "notarization untested — no Apple account yet") — release docs never overstate.

## Verification checklist
- [ ] No production key material touched/generated/handled by the agent
- [ ] Publish jobs gated behind `release` Environment; no publish-on-push anywhere
- [ ] Draft-release flow verified in a real run (URL recorded)
- [ ] Channel IDs, signatures, manifest schema validated in CI
- [ ] RELEASING.md runbooks consistent with the implementation

## Common pitfalls
- "Just a tiny publish step" outside the gate — the classic footgun; refuse.
- Mixing OS code-signing with updater signatures in docs/UI copy (three layers, ADR-0005 §2).
- Believing static updaters can downgrade — they can't; supersede instead and say so.
- Treating prerelease manifests as stable (GitHub `/releases/latest` excludes prereleases — re-verified in S4).
